# Localisation (i18n)

> **Status: scaffolding in place, English + French, extraction in progress.**
> The engine, the provider, the picker and the food-alias table are done and
> tested. The shell, Fuel (nutrition), Progress, the check-in, XP and the meal
> modal are translated. Screens that have not been visited yet still render
> their original English strings — the mechanism below is how they get done,
> not a promise that they already are.

The app ships in **English** and **French**. French first is not arbitrary:
Morocco is the home market and the food vocabulary is where a translator-less
approach falls over (see §4).

---

## 1. Where things live

| Piece | File | Notes |
| --- | --- | --- |
| Catalogues + engine | `packages/core/src/i18n.ts` | Pure, no React. Both locales in one file so a missing translation is visible next to its English source. |
| React provider | `src/lib/i18n-context.tsx` | `useI18n()` / `useT()`, sets `<html lang>` and `dir`. |
| Picker | `src/components/features/diet-preferences.tsx` | Personalize → diet + language. |
| Food aliases | `FOOD_ALIASES` in `packages/core/src/nutrition.ts` | Local *names* for the 41 foods, next to `FOOD_DB`. |
| Tests | `packages/core/tests/i18n.test.ts` | Catalogue shape, plural parity, locale resolution, cognate allowlist. |

## 2. Using it

```tsx
const { t, locale, setLocale } = useI18n();

t('fuel.plan.title');                       // 'What to eat next'
t('diet.available', { allowed: 12, total: 41 }); // '{allowed} of {total} foods…'
t('checkin.session', { count: 3 });         // plurals: picks .one / .other
```

Rules the tests enforce:

- **Keys are `area.thing` in camelCase**, no hyphens (`diet.rule.noPork`). The
  grammar is asserted, so the catalog cannot drift into three conventions.
- **English is the reference.** `catalogGaps('fr')` must report no missing and
  no extra keys, and every message must be a non-empty string or a complete
  plural.
- **Plurals carry the same placeholders in both languages.** A translation that
  forgets `{count}` fails rather than rendering `undefined`.
- **Identical EN/FR strings are an explicit allowlist**
  (`INTENTIONAL_COGNATES`). Copy-pasting the English into the French field is
  the single most likely way this system rots, so the test asserts the
  identical set is *exactly* the declared cognates — a new untranslated string
  fails the build until it is translated or listed with a reason.

### Output outside React

Server code and the mobile app import `translate` from `@smartfit/core`
directly; the React provider is only needed for re-render-on-change.

## 3. Locale resolution

`resolveLocale(stored, deviceLanguages)` picks in this order:

1. `profile.locale` — an explicit choice, synced to Firestore and to mobile.
2. The device language list, matched on the base tag (`fr-MA` → `fr`).
3. English.

Two deliberate details in the provider:

- The device language is read **after mount**, never during render. Reading
  `navigator.languages` while rendering produces different markup on the server
  and the client, which React reports as a hydration mismatch on every page.
- `useI18n()` works **outside** the provider, falling back to the device
  language. The public landing page has no store and shares components with the
  dashboard; a component should not have to know where it is rendered.

## 4. Food is not a normal string

A translated interface is not a localised scanner. `parseMealDescription`
matches food words, so "poulet" has to resolve to `chicken` — translation
alone would leave a French user typing perfectly good French at a table that
only understands English.

`FOOD_ALIASES` holds local names per locale, and `foodLabel(food, locale)`
returns the display name, so a French user reads "Poulet" while the id stays
`chicken` in storage. **Aliases are additive**: the English names stay in
`FOOD_DB[].names` and always match, so a shared meal log keeps working when the
athlete switches languages.

When adding a food: add the English name in `FOOD_DB`, then the local names in
`FOOD_ALIASES`, and the scanner test (`packages/core/tests/nutrition.test.ts`)
proves the word resolves.

## 5. Translating a screen

1. Replace the literals with `t('area.thing')`, using an existing area prefix.
2. Add the English entry under the right section comment.
3. Add the French entry **in the matching position** in the `fr` block — the two
   blocks are kept in the same order so a diff shows the translation next to its
   source.
4. `pnpm --filter @smartfit/core test` — the catalogue tests catch a missing
   key, a stray placeholder and a forgotten translation.

Copy that is asserted by the E2E suite (`Save meal`, `Scan`, `Log meal`) is
translated **under the same English string** so those journeys keep passing in
the default locale. If a selector must change, change it in `e2e/` in the same
commit.

## 6. Not done yet

- Screens outside the shell/Fuel/Progress/meal-modal path still hold literals
  (library, plan, run, body, admin, tenant console, coaching).
- Email/notification copy is server-side English.
- No right-to-left locale. `localeDir()` exists and the provider applies `dir`,
  so adding Arabic is a catalogue plus a font/QA pass, not a refactor — but it
  has not been done and should not be claimed.
- No translation management tooling. Two locales in one file is the right size
  for this; a third would justify moving each locale to its own module.
