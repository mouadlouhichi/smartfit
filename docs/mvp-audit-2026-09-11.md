**Scope:** web user journey, workout loop, onboarding, navigation, empty/error/offline states,

## 0. Executive verdict

### The short answer

**SmartFit is a credible local-first web MVP and a good controlled beta candidate. It is not yet a
production-ready cloud or paid SaaS MVP.** The core loop is unusually complete for a small product:
there is real onboarding, a schedule, a guided workout runner, set-level logging, progress and body
trends, a dedicated GPS run flow, export/delete controls, and honest local/offline fallbacks.

The launch decision depends on scope:

| Proposed launch | Decision | Why |
| --- | --- | --- |
| Local-only web beta, no paid plans | **Conditional GO** | The product loop works and automated checks are green; do a real-device smoke pass first. |
| Public web app with Firebase accounts | **CONDITIONAL NO-GO** | The server-owned deletion job and stricter rules are now implemented, but they still need Java-enabled emulator coverage, staging deployment, Admin env configuration, and a real two-device smoke pass. |
| Paid Pro / charging money | **NO-GO** | Billing, entitlement provisioning, restore, cancellation, refund handling, and server-side Pro enforcement are not implemented. The UI and landing page now explicitly describe Pro as a disabled preview. |
| Expo mobile launch | **NO-GO** | `apps/mobile` remains a local-only prototype with no auth, cloud sync, onboarding, coach, run tracker, or Pro parity. It is explicitly descoped. |

**Overall UX/MVP confidence: 7/10 for local web; 4/10 for cloud production; 1/10 for paid
monetisation.** This is a scope/operational rating, not a visual-design rating.

### Highest-severity remaining blockers

1. **Cloud account deletion now has a server-owned retryable job**: the client reauthenticates,
   sends a fresh ID token, and `POST /api/account/delete` recursively removes the user tree before
   deleting Auth. The job record handles a dropped response or a failed Auth deletion without
   falling back to a client-side wipe. It still needs Admin env configuration and a staging failure-
   injection test before public launch. Evidence: `src/app/api/account/delete/route.ts`,
   `src/lib/firebase/admin.ts`, `src/lib/firebase/auth-context.tsx`, and
   `src/components/dashboard/screens/profile-screen.tsx`.
2. **Firestore rules and indexes have not been verified in this environment or against the
   deployed project.** The rules test command is currently blocked before tests run because Java is
   unavailable. The CI rules job is now blocking and includes the paid-stamp, profile-bound, full GPS
   session, and nested collection coverage. Evidence: `firestore.rules`, `firestore.indexes.json`,
   `tests/rules/firestore-rules.test.ts`, `firebase.json`, and the failed local `pnpm test:rules` run.
3. **Paid billing is not a launchable feature.** There is no Stripe webhook/Admin provisioning,
   CMI checkout/callback, trusted restore/cancel path, or entitlement lifecycle. Paid checkout is
   now disabled in `src/components/dashboard/modals/pro-modal.tsx`; public copy in
   `src/components/landing/pricing-section.tsx`, `src/components/landing/faq-section.tsx`,
   `README.md`, and `src/app/terms/page.tsx` has been brought into parity.
4. **The browser journeys have not actually run in this environment.** Playwright stopped at
   browser launch because Chromium installation failed with `ECONNRESET`; no E2E assertion ran.

## 1. What was re-verified and fixed in this pass

### 1.1 Data integrity and identity isolation

| Finding from prior review | Current status | Evidence |
| --- | --- | --- |
| Signed-out cloud state could leak through the shared local key | **Fixed and re-verified statically** | `src/lib/store-context.tsx` uses owner-bound snapshots and `smartfit.cache.{uid}`; `src/lib/hydration.ts`; `tests/hydration.test.ts`. |
| Same-key queue collapse could replace the in-flight item and then shift away the newest write | **Fixed in this pass** | `src/lib/firebase/write-queue.ts`: only pending items collapse; the in-flight head is preserved. Regression test: `tests/write-queue.test.ts` (“keeps the newest same-key write queued…”). |
| Cloud history was unbounded | **Fixed in the current tree** | `src/lib/firebase/repo.ts` uses bounded initial queries; `src/components/dashboard/screens/plan-screen.tsx` and `body-screen.tsx` call the paging APIs; `collectFullState()` pages for export. |
| Destructive operations could race queued writes | **Fixed for client reset; account deletion moved server-side** | `src/lib/store-context.tsx` flushes before `clearData`, `replaceState`, and sign-out; `WriteQueue.flush()` waits for in-flight work. Account deletion uses the retryable Admin job in `src/app/api/account/delete/route.ts`. |
| Local GPS recovery draft was global | **Fixed in this pass** | `src/lib/run-sensors.ts` scopes drafts by owner; `RunRecord` passes the Firebase uid; sign-out/account changes clear drafts. |
| Coach chat and AI-use counters were global | **Fixed in this pass** | `src/components/dashboard/coach-panel.tsx` scopes both keys by Firebase uid or local/signed-out bucket. The cap remains client-side and therefore is not an entitlement/security boundary. |
| Client could mint Pro stamps in Firestore | **Hardened; requires emulator verification** | `firestore.rules` rejects client-created trial and paid stamps, preserves only an exact server-provisioned paid stamp, and `store-context.tsx` strips local Pro previews during cloud import; `tests/rules/firestore-rules.test.ts` covers the boundary. |

### 1.2 User-facing correctness fixes

- **Onboarding finish is now one cloud batch**: `src/lib/firebase/repo.ts` adds
  `saveOnboarding()`, and `src/lib/store-context.tsx` passes the first goal with the profile so a
  successful onboarding cannot persist `onboardingDone` while losing the promised goal.
  `src/app/onboarding/page.tsx` stays on the page with an alert when the strict flush fails.
- **Backup replace no longer wipes first**: `replaceUserState()` in `src/lib/firebase/repo.ts`
  upserts/removes collection rows before saving the profile. A failed upload can leave a mixed
  state that can be retried, but it no longer turns a healthy account into an empty account before
  the import has had a chance to upload.
- **Run home totals now match bars**: `src/components/dashboard/run/run-home.tsx` computes the
  headline and comparison from tracked runs, not all cardio sessions.
- **Run history honours the configured week start**: `src/components/dashboard/run/run-history.tsx`
  uses `weekStartOf(state)` instead of a hard-coded Monday.
- **Share pace rounding is corrected**: `src/components/dashboard/share-sheet.tsx` now turns a
  rounded `5:60` into `6:00`.
- **Logged set detail includes load and units**: `src/components/dashboard/modals/SessionDetailModal.tsx`
  uses the shared `formatSet()` formatter.
- **Guided set metadata is now captured honestly**: the runner exposes working, warm-up, drop,
  and failure set types plus optional RPE 1–10; warm-ups remain visible but are excluded from
  coaching volume, PRs, muscle counts, and the finish summary. CSV export preserves the metadata.
- **Weight-unit changes preserve the target**: `src/components/dashboard/screens/profile-screen.tsx`
  and onboarding convert the visible target value while retaining canonical kilograms.
- **Completed daily plans no longer masquerade as pending**: `src/components/dashboard/screens/overview-screen.tsx`
  distinguishes the next unfinished slot from an all-done plan and uses a native button instead of
  a keyboard-fragile `div[role=button]`.
- **Destructive deletion now reauthenticates Google users before the wipe**: `src/lib/firebase/auth-context.tsx`
  supports password credentials and Google popup reauthentication; `profile-screen.tsx` surfaces
  failures instead of silently proceeding.
- **Sign-out shows progress and waits for writes**: `profile-screen.tsx` disables the action while
  `signOutAndForget()` drains/parks the queue and clears account-scoped local traces.
- **Pro surface is visually contained and explicitly disabled for real billing**:
  `pro-modal.tsx` is positioned relative to its dialog and does not open a real payment link in
  this release.

## 2. Full journey review

### 2.1 Discovery → login → onboarding

**Strengths**

- The landing page has a coherent promise, clear training categories, feature proof, privacy,
  pricing/preview, FAQ, legal links, and a route to `/login`.
- `/login` correctly distinguishes local mode from cloud mode instead of showing an unusable auth
  form when Firebase is absent. Cloud mode supports email/password, Google, reset, verification
  resend, friendly errors, and a profile/onboarding gateway.
- `src/app/dashboard/layout.tsx` / `AuthGate` enforce both auth and `onboardingDone` on deep links,
  avoiding a dashboard flash for an incomplete profile.
- Onboarding collects name, units, rest days, week start (through the profile defaults), plan,
  optional target weight/gym, and a real first goal. It now has visible save failure handling.

**Remaining UX gap — P1 / retention**

- Onboarding now seeds the selected gym's suggested week in the same completion batch, so a new
  athlete can see a real first schedule immediately. A direct “Start workout 1” CTA and a no-gym
  plan-derived template remain a conversion enhancement, not a data-integrity blocker.
- Email verification is sent but not required before using cloud data. This is an intentional
  low-friction policy for now; enforce verification before a public abuse-sensitive launch if the
  Firebase project needs it.

### 2.2 Core workout loop

**Current path**

`OverviewScreen` → one-tap log or “Start today’s workout” → `session-runner-modal.tsx` → exercise
images/picker, set rows, rest timer, haptic/chime, PR/progression feedback, summary → save →
`SessionDetailModal` → edit/delete. Manual logging remains available from the global CTA and
mobile navigation.

**Strengths**

- Schedule entries carry exercise templates and `scheduleId`; the plan and log reconcile through
  `todaysAgenda()` rather than decorative cards.
- The runner supports adding/removing exercises mid-session, adding sets, previous performance,
  suggested rest, adaptive targets in the preview gate, notes, and a finish summary.
- Detail now renders exercises, reps, load, units, distance, notes, route/share data, and edit/delete.
- Records, achievements, volume, goals, and body trends are derived from the same canonical state.

**Remaining P1/P2**

- The runner now supports working, warm-up, drop, and failure set types plus optional RPE. Warm-ups
  remain visible in history but are excluded from volume/PR coaching metrics; manual log still uses
  the simpler exercise-count form and does not expose the set classification controls.
- Manual log still asks many fields in one modal; defaults/collapsible “details” would reduce first
  workout friction.
- A real-device runner pass is still mandatory: lock screen, permission denial, haptics/audio,
  long GPS gaps, browser tab suspension, and one-handed target sizes were not executable here.

### 2.3 Run loop

`/dashboard/run` has a separate Record/History/Records IA. GPS permission, weak accuracy, no GPS,
auto-pause, moving time, splits, elevation, wake lock, route map fallback, recovery, summary, share
card, history, and personal records are all represented in:

- `src/components/dashboard/run/run-record.tsx`
- `src/lib/run-sensors.ts`
- `src/components/dashboard/run/run-map.tsx`
- `src/components/dashboard/run/run-history.tsx`
- `src/components/dashboard/run/run-records.tsx`
- `packages/core/src/run.ts`

The main remaining risk is platform behavior, not missing UI: web geolocation, WebGL/vector tiles,
raster tile availability, wake lock, and browser backgrounding vary by phone/browser. The code has
fallbacks, but only a real device matrix can establish “run-ready”. GPS traces are sensitive data;
the owner-scoped draft cleanup added in this pass is required for account privacy.

### 2.4 Retention and value loops

**Present:** rest-day-aware streak, weekly goals, rings, heatmap, achievements, records, coach, weekly
summary, share cards, suggested program, export, and an installable PWA shell.

**Missing or weak:** no push reminders, no weekly review notification, no proactive coach nudges,
no goal-at-risk state, no streak-freeze/adherence model beyond the current rest-day tolerance, and
no post-workout celebration/share for ordinary strength sessions. These are P1/P2 retention work,
not blockers for a private logging beta.

## 3. State, cloud, offline, and destructive lifecycle

### Local mode

`src/lib/hydration.ts`, `src/lib/store-context.tsx`, and `@smartfit/core` provide defensive parsing,
local persistence, cross-tab adoption, owner-aware cloud caches, storage-quota warning, JSON/CSV export,
and erase. Local mode is the most coherent MVP scope: no auth dependency, no cloud outage, and no
paid expectation.

**Caveat:** the unsigned local bucket is intentionally shared by anyone using the same browser
profile. A new cloud account may be offered leftover local data for manual import. That is honest but
not suitable for shared/public kiosk devices; add an explicit “this browser’s local data may belong to
another user” warning or a local-profile picker if that deployment matters.

### Cloud mode

- Firebase Auth and Firestore are lazy-loaded; persistent IndexedDB cache and a per-account
  `localStorage` mirror support offline reads.
- The write queue serializes operations, retries transient failures, parks rules failures, exposes a
  sync banner/retry, and now preserves an in-flight same-key write.
- Initial time-series reads are bounded and the Plan/Body screens page older records. Export pages
  the full history and refuses to download if a page cannot be fetched.
- Firestore ownership, profile/record bounds, and the no-client-Pro-stamp boundary are in
  `firestore.rules`; they still need emulator and staging verification.

**Remaining P1**

- Cross-device conflict semantics are now explicit: Firestore's last successful document write wins;
  there is no field-level merge. The queue is ordered per tab, not globally, so high-value edits should
  be exported before editing from two devices. A revision/conflict UI remains a future collaboration
  feature rather than an unspoken promise.
- `collectFullState()` now refuses to download when a cloud page cannot be loaded, instead of silently
  presenting a partial backup as complete. The user gets a retryable error and the paging cursor stays
  available.
- App Check is optional in code and enforcement is an external Firebase-console step. A production
  deployment must prove it is enabled in the intended order and monitor rejected clients.

### Destructive data and account deletion

Client reset/sign-out coordination is materially safer: destructive actions wait for queued writes,
and wrong/cancelled reauthentication no longer wipes first. Account deletion now uses a server-owned
retryable job: `POST /api/account/delete` verifies a recent ID token, records progress outside the user
tree, recursively deletes all nested Firestore data, then deletes Auth. It must still be configured
with Admin credentials and tested in staging with injected Firestore/Auth failures before cloud launch.

## 4. Billing, Pro, and marketing parity

### Current truth

The repository contains a useful Pro feature-gate preview (`packages/core/src/pro.ts`) and a sandbox
for local product testing. It does **not** contain a production entitlement system:

- no Stripe webhook route or Admin SDK receipt provisioning;
- no CMI checkout/callback;
- no secure restore, refund, expiry, grace-period, or cancellation model;
- Firestore cannot independently verify a paid receipt from a client;
- the AI “6 replies/day” counter is local browser state and can be cleared/bypassed;
- mobile does not enforce the web gates.

This pass deliberately prevents the UI from opening configured payment links or activating a cloud
paid account. `docs/billing.md` is now a go-live contract rather than an assertion that billing is
live. Public pricing/FAQ/terms/README copy now calls Pro a **preview**, not a purchasable tier.

**Launch rule:** do not turn on Stripe/CMI or advertise prices until the server provisioning, account
mapping, entitlement rules, restore/cancel/refund behavior, and billing tests exist. If monetisation is
required for the MVP, it is a separate milestone, not a checkbox.

### Marketing parity check

- Local/cloud privacy language was corrected in `src/components/landing/features-section.tsx`,
  `src/components/landing/faq-section.tsx`, and `src/app/terms/page.tsx`.
- `src/components/landing/pricing-section.tsx` and `free-list-section.tsx` no longer promise a live
  paid trial.
- The mobile disclaimer in `README.md` and `docs/ops-runbook.md` is consistent with the actual Expo
  scope.
- Remaining copy review: exercise-image/CDN licensing and third-party map/tile dependency terms
  must be cleared for any commercial launch. README already calls out the ExerciseDB artwork issue,
  but this needs a release owner and written license decision.

## 5. Accessibility, responsive behavior, and error states

### Good foundations

- Radix dialog/label/select primitives, focus-visible styles, semantic buttons, live toast/status
  regions, keyboard date picker, explicit labels, mobile bottom navigation, and dialog bottom-sheet
  behavior are present.
- Reduced-motion handling exists for page/sheet/runner transitions.
- Responsive layouts are intentionally mobile-first; runner controls and share sheets have separate
  small-screen treatment; the desktop rail yields to mobile navigation.
- Error boundaries (`src/app/error.tsx`, `global-error.tsx`), offline route, storage warning, sync
  banner, GPS error/weak states, AI fallback, and empty states exist.

### Remaining P1 accessibility/UX verification

- No automated axe/keyboard/screen-reader run is in the suite. The Playwright suite could not launch,
  so focus return, dialog swipe/escape behavior, tab order, and screen-reader names remain unverified.
- Run-week bars, active-minute charts, body trends, intensity spread, and muscle-volume displays
  now expose screen-reader text/list alternatives. The remaining accessibility work is device-level
  verification of focus, announcements, contrast, and touch targets.
- GPS/live runner should get a VoiceOver/TalkBack pass: fixed status announcements, permission error
  recovery, paused/recording state, and set controls without looking at the screen.
- Share previews use blob URLs and external basemap art; verify download/share behavior in Safari iOS
  and Android Chrome, not only desktop Chromium.

### Empty/offline/error state quality

The app is honest about no data and usually has an action. Sync and AI failures are visible and local
mode continues to work. The largest remaining copy risk is that “saved locally” can be read as
“guaranteed durable” when localStorage is disabled/full; the storage warning exists, but it should be
near the save action for high-value edits. Network loss during a multi-collection import or deletion
needs the explicit retry/recovery job described above.

## 6. Mobile scope

`apps/mobile` is an Expo local-only prototype. It has AsyncStorage screens and a subset of the domain,
but no documented parity for Firebase Auth, onboarding, cloud persistence, coach, GPS run recording,
Pro gates, account deletion, or the web's full error/offline UX. It should remain out of launch claims,
store listings, and user-facing navigation. The current README and ops runbook now say so.

If mobile becomes part of the MVP, fund a separate parity project: auth + deletion, shared hydration,
cloud sync/conflict policy, onboarding, native GPS/background behavior, offline tests, privacy/data
safety forms, and a device test matrix.

### Paid release

- [ ] Implement and test Stripe/CMI server provisioning, verified user mapping, restore, cancel,
      expiry/grace/refund, and trusted entitlement reads.
- [ ] Keep Firestore rules closed to client paid-stamp creation; run the emulator tests.
- [ ] Move coach quotas/entitlements server-side or remove the Pro claim.
- [ ] Only then restore public pricing and payment CTAs.

**Final recommendation:** the local web product is ready for a clearly labelled beta after the
manual device pass. Cloud beta is conditional on the rules job, staging deployment, Admin deletion
configuration/test, and two-device smoke pass. Do not take money until the separate billing milestone
is implemented.
